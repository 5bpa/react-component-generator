# Commit

변경사항을 읽고 의미 단위로 나눠, 일관된 한국어 커밋 메시지로 남긴다. 사용자가 커밋을 요청한 것 자체가 승인이므로 별도 확인 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석
아래를 병렬로 실행해 현황을 파악한다.

- `git status --short` — 수정/추가/삭제/untracked 파일 목록
- `git diff` (unstaged) 와 `git diff --staged` (staged) — 실제 변경 내용
- `git log --oneline -10` — 이 저장소의 기존 메시지 스타일 확인

변경이 없으면 "커밋할 변경사항이 없다"고 알리고 종료한다. git 저장소가 아니면 그 사실을 알리고 종료한다.

diff가 크면 파일별로 나눠 읽는다. 파일 이름만 보고 판단하지 말고 무엇이 왜 바뀌었는지 내용을 확인한다.

### 2. 논리적 단위로 분류
한 커밋은 하나의 목적만 담아야 이력을 읽거나 revert 하기 쉽다. 변경 파일을 목적별로 묶는다.

- 새 기능과 그 기능 때문에 생긴 테스트·타입은 같은 커밋
- 버그 수정과 무관한 포맷팅·리팩터링은 분리
- 의존성/설정 변경은 코드 변경과 분리
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p` 로 hunk 단위 분리를 고려하되, 대화형 플래그가 막혀 있으면 사용자에게 알리고 한 커밋으로 묶을지 묻는다

전부 하나의 목적이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성
형식:

```
<type>: <요약>

<본문 (선택)>
```

type:
| type | 용도 |
|------|------|
| feat | 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·문서 등 잡무 |

작성 규칙:
- 요약은 한국어, 50자 내외, 마침표 없이 "무엇을 했는지" 서술 (예: `feat: 컴포넌트 생성 폼에 props 입력 필드 추가`)
- 본문은 요약만으로 부족할 때만, "왜" 바꿨는지 중심으로 쓴다. diff를 말로 되풀이하지 않는다
- 기존 `git log` 에 scope 나 다른 관례가 뚜렷하면 그 관례를 우선한다
- 시스템 프롬프트/리마인더에 커밋 attribution(Co-Authored-By 등) 지침이 있으면 메시지 끝에 따른다

### 4. 바로 커밋
승인 절차 없이 곧바로 진행한다.

1. 커밋마다 해당 파일만 이름으로 `git add <파일...>` (`git add -A`/`.` 는 비밀 파일·불필요한 파일이 딸려갈 수 있어 피한다)
2. `git commit -m` 으로 커밋 (여러 줄은 HEREDOC 사용)
3. 끝나면 `git log --oneline -n <커밋 수>` 로 결과 확인 후, 만든 커밋 목록(메시지와 파일)을 사용자에게 보고한다

사용자가 이후 수정을 원하면 그때 amend/reset 으로 대응한다.

## 주의
- `.env`, 키·토큰·인증서 등 민감 파일이 변경 목록에 있으면 커밋 대상에서 빼고 사용자에게 알린다
- 승인 생략은 커밋에만 해당한다. push, amend, `--no-verify` 는 사용자가 요청하지 않는 한 하지 않는다
- 논리적 단위 분리가 애매해 사용자 판단이 꼭 필요한 경우(예: 한 파일에 섞인 변경을 쪼갤 수 없을 때)에만 질문한다
- pre-commit hook 이 실패하면 우회하지 말고 원인을 보고하고 고친 뒤 새 커밋으로 만든다
