# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것을 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하거나 충돌하지 않는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리, 에러 매핑)
- **유틸 / 순수 함수**
- **버그 수정** (재현 테스트를 먼저 작성하고 실패를 확인한 뒤 고친다)

### TDD 불필요

- **타입 정의**
- **설정 파일**
- **순수 UI** (로직 없는 마크업·스타일)
- **SQL**

판단이 애매하면 로직(분기·계산·상태 변경)이 있는지 본다. **로직이 있으면 적용**한다.

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. import 오류, 오타, 문법 오류, 잘못된 셋업으로 인한 실패는 RED가 아니다. 테스트를 고치고 다시 실행한다.

### 2. GREEN — 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능, 일반화, 옵션은 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 통과를 확인한다.
- 하나라도 실패하면 REFACTOR로 넘어가지 않는다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.** 요구된 모든 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 복사해 두고 보며 다시 치기 모두 해당한다.
- 삭제한 코드는 테스트로부터 다시 이끌어낸다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없는데 회귀를 막는다. 단순하다는 판단이 자주 틀리는 지점이다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현이 통과시키는 것을 확인할 뿐, 요구를 검증하지 않는다. 실제로 추가되는 경우도 드물다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 TDD가 빠르다. |
| "삭제하면 낭비" | 매몰 비용이다. 검증 안 된 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 삭제하고 RED부터 시작한다. |
| "프로토타입이다" | 프로토타입은 곧잘 프로덕션이 된다. 버릴 코드라면 테스트 없이 작성하되 저장소에 커밋하지 않는다. 남길 코드라면 TDD를 적용한다. |
